# Celery 실행 풀 비교: Prefork vs Gevent

## 개요

Celery는 태스크를 병렬로 처리하기 위해 다양한 **실행 풀(Execution Pool)** 방식을 지원합니다. 대표적으로 `prefork`(기본값)와 `gevent`가 있으며, 시스템의 작업 특성에 따라 적합한 방식이 다릅니다.


## 작업 유형 구분

### CPU Bound 작업

- **정의**: CPU 연산이 집중되는 작업
- **예시**: 이미지 처리, 수학적 계산, 데이터 압축, 암호화
- **특징**: 작업 시간의 대부분을 CPU가 실제로 연산하는 데 사용

### I/O Bound 작업

- **정의**: 외부 시스템과의 입출력을 기다리는 작업
- **예시**: HTTP API 호출, 데이터베이스 쿼리, 파일 읽기/쓰기, LLM API 호출
- **특징**: 작업 시간의 대부분을 응답을 기다리는 데 사용 (CPU는 거의 쉬고 있음)


## Prefork 방식 (기본값)

### 동작 원리

Prefork는 **프로세스 기반** 병렬 처리 방식입니다.

```
메인 프로세스
    │
    ├── 워커 프로세스 1 (태스크 A 처리)
    ├── 워커 프로세스 2 (태스크 B 처리)
    ├── 워커 프로세스 3 (태스크 C 처리)
    └── 워커 프로세스 4 (태스크 D 처리)
```

`worker_concurrency=4`로 설정하면 4개의 독립된 프로세스가 생성되고, 각 프로세스가 하나의 태스크를 처리합니다.

### I/O Bound 작업에서의 문제점

외부 API를 호출하는 HTTP 노드가 있다고 가정해봅시다:

```python
# 워커 프로세스 1이 이 태스크를 실행
def execute_http_node():
    response = requests.get("https://external-api.com/data")  # 3초 소요
    return response.json()
```

**실행 타임라인:**

```
시간 →  0초      1초      2초      3초      4초
        ├────────┼────────┼────────┼────────┤

프로세스 1: [태스크 시작] [  API 응답 대기 (대기중...)  ] [처리] [완료]
                         ↑
                         이 3초 동안 프로세스 1은 아무것도 안 함
                         하지만 "사용 중" 상태로 표시됨
                         다른 태스크를 받을 수 없음
```

**4개 프로세스가 모두 I/O 대기 중인 경우:**

```
프로세스 1: [──────── API 응답 대기 ────────]
프로세스 2: [──────── DB 쿼리 대기 ────────]
프로세스 3: [──────── LLM 응답 대기 ────────]
프로세스 4: [──────── 파일 업로드 대기 ────────]

큐:        [태스크5] [태스크6] [태스크7] ...
                     ↑
                     대기 중 (처리할 프로세스 없음)
```

4개 프로세스 모두 실제로는 CPU를 거의 사용하지 않으면서도, 새로운 태스크를 처리할 수 없는 상태가 됩니다.

### Prefork의 장단점

| 장점                               | 단점                          |
| ---------------------------------- | ----------------------------- |
| Python GIL 우회 (진정한 병렬 처리) | 프로세스당 메모리 사용량 높음 |
| CPU Bound 작업에 최적              | I/O 대기 시 리소스 낭비       |
| 프로세스 격리로 안정성 확보        | 프로세스 생성/관리 오버헤드   |


## Gevent 방식

### 동작 원리

Gevent는 **코루틴(Greenlet) 기반** 병렬 처리 방식입니다.

```
단일 프로세스
    │
    ├── Greenlet 1 (태스크 A)
    ├── Greenlet 2 (태스크 B)
    ├── Greenlet 3 (태스크 C)
    ├── ...
    └── Greenlet 1000 (태스크 N)
```

하나의 프로세스 내에서 수백~수천 개의 경량 코루틴이 협력적으로 실행됩니다.

### 핵심 개념: 협력적 멀티태스킹

Gevent의 핵심은 **I/O 대기 시 자동으로 다른 코루틴에게 실행권을 양보**하는 것입니다.

```python
# Greenlet 1이 실행
def execute_http_node():
    response = requests.get("https://external-api.com/data")
    #          ↑
    #          여기서 I/O 대기 발생!
    #          Gevent: "기다리는 동안 다른 Greenlet 실행할게"
    return response.json()
```

**실행 타임라인:**

```
시간 →  0초      1초      2초      3초      4초
        ├────────┼────────┼────────┼────────┤

[단일 프로세스 내부]

Greenlet 1: [시작][대기...                    ][재개][완료]
Greenlet 2:      [시작][대기...         ][재개][완료]
Greenlet 3:           [시작][대기...][재개][완료]
Greenlet 4:                [시작][처리][완료]
Greenlet 5:                     [시작][대기...][재개]...

                 ↑
                 대기 시간에 다른 Greenlet이 실행됨
                 CPU 유휴 시간 최소화
```

### I/O Bound 작업에서의 효율성

동일한 상황에서 Gevent는:

```
[단일 프로세스]
├── Greenlet 1: API 호출 → [대기: 양보] → 응답 수신 → 처리
├── Greenlet 2: DB 쿼리 → [대기: 양보] → 결과 수신 → 처리
├── Greenlet 3: LLM 호출 → [대기: 양보] → 응답 수신 → 처리
├── Greenlet 4: 파일 업로드 → [대기: 양보] → 완료 → 처리
├── Greenlet 5: 바로 실행 가능! (기존에는 대기해야 했음)
├── Greenlet 6: 바로 실행 가능!
└── ...

→ I/O 대기 시간을 활용하여 더 많은 태스크 동시 처리
```

### Gevent의 장단점

| 장점                          | 단점                                     |
| ----------------------------- | ---------------------------------------- |
| 단일 프로세스로 높은 동시성   | CPU Bound 작업에는 부적합                |
| 메모리 효율성 우수            | C 확장 라이브러리 호환성 주의 필요       |
| I/O Bound 작업에 최적         | 디버깅이 상대적으로 어려움               |
| 컨텍스트 스위칭 오버헤드 낮음 | 몽키 패칭으로 인한 예상치 못한 동작 가능 |


## 비교 요약

| 항목            | Prefork                   | Gevent                            |
| --------------- | ------------------------- | --------------------------------- |
| 병렬 처리 단위  | 프로세스                  | 코루틴 (Greenlet)                 |
| 동시성 4개 의미 | 4개 태스크 동시 처리      | 수백~수천 I/O 작업 동시 처리 가능 |
| I/O 대기 시     | 프로세스가 묶여있음       | 다른 Greenlet으로 전환            |
| 메모리 사용량   | 높음 (프로세스당 수백 MB) | 낮음 (Greenlet당 수 KB)           |
| 적합한 작업     | CPU Bound                 | I/O Bound                         |


## 현재 시스템에 대한 결론

Moduly 워크플로우 엔진은 다음과 같은 I/O Bound 작업이 주를 이룹니다:

- LLM API 호출 (OpenAI, Anthropic 등)
- 외부 HTTP API 호출
- 데이터베이스 조회/저장
- 파일 업로드/다운로드

따라서 현재 `prefork` 방식보다는 `gevent` 방식이 더 적합합니다. 전환 시 예상되는 효과:

- 동일 리소스로 더 많은 동시 요청 처리 가능
- 메모리 사용량 감소
- 응답 시간 개선 (큐 대기 시간 감소)
