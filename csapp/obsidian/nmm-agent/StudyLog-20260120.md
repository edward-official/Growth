워크플로우 엔진의 노드 실행 함수를 비동기로 전환한 후 로그 시스템에서 발생하는 문제를 분석한 문서입니다.


## 발생 현상

1. **성공한 노드가 실패로 표시됨**: 정상적으로 실행 완료된 노드인데 로그에서 FAILED 상태로 표시
2. **로그 누락**: 특정 노드의 실행 로그가 아예 보이지 않음
3. **중복 로그**: 동일한 노드의 로그가 여러 번 등장


## 문제 원인: Celery 태스크 실행 순서 미보장

### 현재 아키텍처

```
WorkflowEngine → WorkflowLogger → Celery Queue → Celery Worker → Database
```

로깅은 두 단계로 이루어집니다:

1. **create_node_log**: 노드 실행 시작 시 호출 (RUNNING 상태로 생성)
2. **update_node_log_finish**: 노드 실행 완료 시 호출 (SUCCESS/FAILED로 업데이트)

### 정상 시나리오

```
시간 ────────────────────────────────────────────────────────────▶

WorkflowEngine:  create_node_log()    node.execute()    update_node_log_finish()
                       │                   │                      │
                       ▼                   │                      ▼
Celery Queue:    [create_node]             │            [update_node_finish]
                       │                   │                      │
                       ▼                   │                      ▼
Celery Worker:   create 처리                │                 finish 처리
                       │                   │                      │
                       ▼                   ▼                      ▼
Database:        INSERT (RUNNING)   ───────────────▶   UPDATE (SUCCESS)
```

### 문제 시나리오

비동기 환경에서 Celery Worker가 Queue에서 태스크를 꺼내는 순서가 보장되지 않습니다.
특히 노드 실행이 매우 빠르게 완료되는 경우(예: 조건 분기 노드) 문제가 자주 발생합니다.

```
시간 ────────────────────────────────────────────────────────────▶

WorkflowEngine:  create_node_log()    node.execute()    update_node_log_finish()
                       │                   │                      │
                       ▼                   │                      ▼
Celery Queue:    [create_node]             │              [update_node_finish]
                       │                   │                      │
                       │    (Celery Worker가 finish를 먼저 처리함)    │
                       │                   │                      │
                       ▼                   ▼                      ▼
Celery Worker:   (대기 중)                              finish 먼저 처리
                       │                                          │
                       │                                          ▼
Database:              │                              SELECT → 레코드 없음!
                       │                                          │
                       │                                          ▼
                       │                              Exception 발생 → retry
                       │                              (3회 retry 후 실패)
                       │
                       ▼
               create 나중에 처리
                       │
                       ▼
Database:        INSERT (RUNNING)  ← 최종 상태가 RUNNING으로 남음
```


## 영향 받는 코드

### workflow_logger.py

```python
def create_node_log(self, node_id, node_type, inputs, process_data=None):
    log_id = uuid.uuid4()
    data = {"id": log_id, ...}
    self._submit_log("log.create_node", data)  # Fire-and-forget (비동기)
    return log_id

def update_node_log_finish(self, log_id, node_id, outputs):
    data = {"log_id": log_id, ...}
    self._submit_log("log.update_node_finish", data)  # Fire-and-forget (비동기)
```

### tasks.py

```python
@celery_app.task(name="log.update_node_finish", bind=True, max_retries=3)
def update_node_log_finish(self, data):
    node_run = session.query(WorkflowNodeRun).filter(...).first()

    if not node_run:
        # 레코드가 없으면 예외 발생 → 3회 retry 후 영구 실패
        raise Exception(f"WorkflowNodeRun not found: log_id={log_id}")

    node_run.status = NodeRunStatus.SUCCESS
    ...
```


## 근본 원인

1. **Fire-and-Forget 패턴**: `send_task()`는 태스크를 Queue에 넣고 즉시 반환
2. **순서 보장 없음**: Celery는 기본적으로 태스크 실행 순서를 보장하지 않음
3. **낮은 Retry 한도**: `max_retries=3`으로 설정되어 create가 늦으면 finish가 실패함
4. **빠른 노드 실행**: 조건 분기 같은 노드는 밀리초 단위로 완료됨
