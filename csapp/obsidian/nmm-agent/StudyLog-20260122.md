# Celery Prefork 방식의 비효율성 분석

## 요약

Moduly 시스템은 I/O bound 작업이 주를 이루므로, 현재 사용 중인 prefork(멀티프로세스) 방식은 **비효율적**입니다.
gevent나 eventlet 같은 코루틴 기반 풀로 전환하면 동일 리소스로 훨씬 높은 동시성을 달성할 수 있습니다.

---

## 현재 설정 분석

### Celery 설정 (`apps/shared/celery_app.py`)

```python
worker_concurrency=4          # 동시 실행 워커 수
worker_prefetch_multiplier=1  # 프로페치 비활성화 (fair scheduling)
worker_max_tasks_per_child=100  # 메모리 누수 방지용 재시작
```

- 별도 `--pool` 옵션 미지정 시 기본값은 **prefork** (멀티프로세스)
- 즉, 4개의 **독립된 프로세스**가 태스크를 처리

---

## Prefork 방식이 I/O Bound에 비효율적인 이유

### 1. 프로세스 단위 블로킹

prefork 방식에서 각 워커는 **독립된 프로세스**입니다.
프로세스가 I/O 대기(HTTP 응답 대기, DB 쿼리 대기) 중이면 해당 슬롯은 **완전히 점유**됩니다.

```
[Worker 1] ████████████████████████████████████░░░░░░░░░░░░░░  (LLM API 대기 - 5초)
[Worker 2] ████████████████████████████████░░░░░░░░░░░░░░░░░░  (DB 쿼리 대기)
[Worker 3] ░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░  (유휴 상태)
[Worker 4] ░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░  (유휴 상태)

█ = CPU 활성    ░ = I/O 대기 또는 유휴
```

4개 중 2개가 I/O 대기 중이면, 새로운 태스크가 큐에 있어도 **유휴 워커로 분배되지 않습니다.**

### 2. 리소스 오버헤드

| 리소스          | prefork (4 프로세스) | gevent (1000 그린렛) |
| --------------- | -------------------- | -------------------- |
| 메모리          | 프로세스당 300-500MB | 그린렛당 4-8KB       |
| 컨텍스트 스위치 | OS 레벨 (비용 높음)  | 유저 레벨 (거의 0)   |
| 동시 처리량     | 4개                  | 수백~수천 개         |

### 3. 현재 태스크의 I/O 특성

#### Workflow Engine 태스크

```python
# execute_workflow, stream_workflow 등
async def execute():
    # LLM API 호출 - 수초~수십초 대기
    response = await llm_client.chat(...)

    # Redis Pub/Sub - 네트워크 I/O
    await publish_workflow_event(...)

    # PostgreSQL 쿼리 - 네트워크 I/O
    session.query(WorkflowDeployment)...
```

**실제 CPU 사용 시간**: 전체 실행 시간의 1-5% 미만

#### Log System 태스크

```python
# create_run_log, update_node_log_finish 등
session.add(run_log)
session.commit()  # DB I/O 대기
```

**순수 I/O bound 작업** - CPU 연산 거의 없음

### 4. 현재 아키텍처의 비효율

현재 코드는 이미 **비동기 패턴**을 사용하지만, prefork 환경에서 이점을 살리지 못합니다:

```python
# workflow_engine/tasks.py
loop = asyncio.new_event_loop()
asyncio.set_event_loop(loop)
result = loop.run_until_complete(engine.execute())  # 동기 블로킹!
loop.close()
```

이벤트 루프를 생성해서 비동기 함수를 실행하지만, **prefork 프로세스 자체가 블로킹**되므로 의미 없습니다.

## 권장 해결 방안

### 방안 1: gevent 풀로 전환

```bash
# 워커 실행 시
celery -A apps.shared.celery_app worker --pool=gevent --concurrency=500
```

장점:

- 동일 메모리로 100배 이상 동시성 확보
- I/O 대기 시 다른 태스크 자동 처리 (협력적 멀티태스킹)
- 기존 동기 코드 수정 최소화 (monkey patching)

주의:

- `gevent.monkey.patch_all()` 호출 필요
- C 확장 라이브러리 호환성 확인 필요

### 방안 2: eventlet 풀로 전환

```bash
celery -A apps.shared.celery_app worker --pool=eventlet --concurrency=500
```

gevent와 유사하지만 일부 라이브러리 호환성 차이 존재

### 방안 3: 순수 async 워커 도입

Celery 대신 **arq**, **dramatiq** 같은 async-native 태스크 큐 사용

장점:

- 현재 async 코드를 네이티브로 실행 가능
- 이벤트 루프 생성/종료 오버헤드 제거

단점:

- 기존 코드 마이그레이션 비용

## 결론

Moduly 시스템의 워크로드(LLM API 호출, DB 쿼리, Redis 통신)는 전형적인 **I/O bound** 패턴입니다.
prefork 방식은 CPU bound 작업에 적합하며, 현재 설정은 리소스 낭비가 심합니다.

**gevent 또는 eventlet 풀로 전환**하면 동일 인프라에서 처리량을 크게 향상시킬 수 있습니다.
