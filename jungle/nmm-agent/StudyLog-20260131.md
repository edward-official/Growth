## 1. Service Separation and Communication Strategy

### Background

Initially, Gateway, Workflow Engine, and Log System were combined in a single monolithic server. Following our coach's advice to adopt Kubernetes, we needed to separate each component into microservices.

### Why Separate the Servers?

At first, I questioned: "Do we really need to separate them?" After all, the monolith was working fine. However, the need for separation came down to **scalability** and **independent deployment**:

| Monolithic                       | Microservices                                       |
| -------------------------------- | --------------------------------------------------- |
| Scale entire system at once      | Selectively scale only bottleneck components        |
| One change → redeploy everything | Deploy only the modified service                    |
| Single Point of Failure (SPOF)   | Fault isolation (one failure doesn't affect others) |

In our system, **the workflow engine had long I/O waits**, while **the Gateway required fast responses**. Scaling them as a single unit was inefficient.

### Why Kubernetes?

Separating into microservices dramatically increases operational complexity. We adopted Kubernetes to address this:

- **Auto-scaling**: Automatically adjust Pod count based on traffic (HPA)
- **Self-healing**: Automatically restart crashed containers
- **Service Discovery**: Automatically manage addresses of dynamically created Pods
- **Declarative Deployment**: Define desired state in YAML and Kubernetes makes it happen

### First Choice: Synchronous HTTP Communication

After service separation, we chose **synchronous HTTP communication** as the most intuitive approach.

### Problem Discovery

However, this choice quickly created bottlenecks:

- The workflow engine is **predominantly I/O-bound** (LLM API calls, external service integrations)
- With synchronous communication, threads block while waiting for I/O completion

### But Why Celery + Redis?

An important question arose: **"Why not just have the three FastAPI servers communicate via async HTTP?"**

FastAPI does support `async/await`, and `httpx` enables async HTTP calls. However, we chose Celery + Redis for these reasons:

| Comparison     | Direct Async HTTP                            | Celery + Redis                          |
| -------------- | -------------------------------------------- | --------------------------------------- |
| Coupling       | Caller must wait for target service response | Fire-and-forget, complete decoupling    |
| Fault Handling | If Engine dies, Gateway times out            | Queue holds tasks until Engine recovers |
| Retry Logic    | Must implement manually                      | Celery provides automatic retries       |
| Load Balancing | Requires load balancer                       | Workers naturally distribute from Queue |
| Task Tracking  | Must implement separately                    | Celery result backend tracks status     |

## 2. Celery Worker Type Optimization: From Prefork to Gevent

### Initial Situation

When adopting Celery Workers, we used the default **Prefork (multi-process)** type without modification.

### Problem Analysis

During operation, we discovered critical issues:

- **Prefork is optimized for CPU-bound workloads**
- Our service is **I/O-bound** (mostly waiting for LLM API responses)
- With Pod CPU allocation limited to 0.2 cores, multi-process caused excessive context switching
- Memory usage increased proportionally with process count (partially due to python ref count)

### Solution: Switch to Gevent Worker

```
# Before: Multi-process (Prefork)
celery -A app worker --pool=prefork

# After: Coroutine-based (Gevent)
celery -A app worker --pool=gevent --concurrency=100
```

## 3. Workflow Engine Performance Optimization

Optimized the workflow engine itself for better performance.

### 3.1 Converting to Async Execution

**Problem**: Node execution functions were synchronous, causing LLM call wait times to directly impact total processing time

**Solution**: Convert all node execution and workflow execution functions to `async/await`

**Caution**: Async conversion can cause concurrent task explosion, so we **adjusted concurrency limits to prevent OOM**

#### But If Each Celery Worker Handles One Task at a Time, Why Async?

Each Gevent Worker greenlet **handles only one Celery Task at a time**. So why make the workflow execution function async?

**Core Reason: Multiple nodes execute within a single Task**

#### Alternative Considered: Sync Function + Internal Event Loop

We also considered: "Why not make `run_workflow()` synchronous and call `asyncio.run()` internally?"

* **Gevent compatibility:** In a fully async design, Gevent can auto-patch the environment and work naturally, whereas using a synchronous entry point with an internal event loop (e.g., `asyncio.run()`) creates a new loop that can conflict with Gevent.
* **Debugging:** Debugging is generally clearer in a fully async architecture because stack traces remain coherent, whereas combining synchronous and asynchronous paradigms often makes tracing execution flow significantly harder.

**Conclusion**: In a Gevent environment, using `async/await` throughout and letting Gevent's monkey patching handle I/O asynchronously proved more stable.

---

### 3.2 Graph Traversal Optimization

**Problem**: Each workflow execution traversed the graph to find the next nodes → unnecessary repeated computation

**Solution**:
- **Pre-analyze workflow graph to generate Adjacency List**
- At execution time, reference the pre-computed adjacency list

---

### 3.3 Parallel Node Execution

**Problem**: Nodes without dependencies were still executing sequentially → unnecessary wait time

**Solution**:
- Perform **Dependency Analysis** based on adjacency list
- Nodes with satisfied dependencies execute **in parallel** using `asyncio.gather()`
